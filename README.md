## 托管数据库是什么？和“云上自建”差在哪

一句话：数据库装在谁的机器上、坏了谁修，是这两种方案的分界线。

常见的部署方式有三种。本地自管：数据库跑在自己机房或私有云里，装机、备份、安全、扩容全靠内部团队；云上自管：数据库装在云服务器（VPS）上，省掉硬件采购，但补丁、备份、高可用仍然是你的事；全托管：数据库作为一种服务直接开通，服务商接走全部运维任务。

按 Google Cloud 的拆法，数据库管理就三类活——设置（预配、部署）、维护（备份、更新、安全）、优化（扩缩、监控、调优）。托管服务把三类全部接走，你保留的是模式设计、查询性能和访问控制，这部分Stripe 的指南里也说得直白：数据怎么建模、谁能访问哪些内容，始终是应用方自己的责任。

自建当然也有它的价值：完全的控制权。但这份控制权的代价是时间——找到合格的 DBA 本身就难，中小企业尤其如此；手动维护还容易引入本可以由自动化避免的错误。控制权和负担，很多时候是同一件事的两面。

| 对比项 | 云服务器自建 | 全托管数据库 |
| --- | --- | --- |
| 装机、系统与数据库安装 | 自己 | 服务商 |
| 备份与恢复 | 自己搭脚本 | 自动执行，控制台恢复 |
| 补丁与版本升级 | 自己安排停机 | 维护窗口自动完成 |
| 高可用 | 自己搭主从 | 选高可用套餐即得 |
| 建模、SQL、权限 | 自己 | 自己（这部分不外包） |

## 单节点还是高可用？差价两倍，收益也写得很清楚

高可用方案就是同等规格的双节点，价格正好是单节点的两倍，换来一个实时同步的备用节点和自动故障切换。

值不值，取决于业务性质：

- 数据丢了能接受重灌、挂了能等几分钟人工修复——单节点足够，博客、后台、开发环境都属于这类。
- 停机直接等于收入损失、用户会打电话投诉——高可用的差价不能省。
- 读多写少、高峰期读压力大——优先加读副本扩读能力，读副本是独立节点、计入账单，不必为了读流量直接上双节点。

算一笔具体的账：$30/月的预算，可以买一个 1 GB 高可用（买冗余），也可以买一个 2 GB 单节点（买性能）。你的业务是怕“慢”还是怕“停”，这笔钱该花在哪就清楚了。

**托管数据库比云服务器自建贵多少，差价买来了什么？**

**数据怎么迁进去？**
标准工具链就够：MySQL 用 mysqldump，PostgreSQL 用 pg_dump/pg_restore。停机窗口紧张的话，先把数据导入追平再做切换。迁移前用按小时计费的实例演练一遍，成本可以忽略不计。

**备份怎么做，能恢复到什么程度？**
托管数据库自带自动备份，可以在控制台从备份恢复出新集群。保留周期和恢复粒度以控制台显示为准；对备份有合规要求的团队，开通前先确认保留期是否达标。
